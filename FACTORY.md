## 1. Seats

| Seat | Owns | Never does | Harness / model |
|---|---|---|---|
| coordinator | plan, assignments, acceptance, stage freeze, final report | write or review product code | see `mandates/coordinator.md` |
| implementer | product source, Dockerfile, RUN.md, commits | accept its own work | see `mandates/implementer.md` |
| reviewer | independent verdict on an exact revision, own probes from the requirement text | fix product code | see `mandates/reviewer.md` |
| retro | numbered requirement checklist, lessons ledger, time and spend log | write product code or issue verdicts | see `mandates/retro.md` |

Seats may share a harness and model. Each seat has its own Band Desktop identity and its
own Git author name and email so commits trace to a seat.

## 2. Workflow

```
human dispatch ──► @coordinator ──► @retro  (checklist + applicable lessons)
                        │
                        ├──► @implementer (full spec + checklist + lessons + repo + checks)
                        │          │ commit + revision + commands + results
                        │          ▼
                        └──► @reviewer (clean checkout, build from RUN.md, supplied checks,
                                        own probes for UNTESTED items) ──► ACCEPT / REJECT
                                                     │ REJECT copies @retro
                                                     ▼
                                     @retro writes lesson ──► next handoff carries it
```

One dispatch per stage, generated by `factory/make_dispatch.py`. A Band room message holds
about 5,000 characters, so the dispatch names the stage's spec file (as the participant
guide's lead-seat example does) and the coordinator reads it; later stages' specs are held
out of the seats' reach until their stage. Every delegated handoff still pastes the complete
task and spec verbatim, as numbered parts sent by `factory/send-parts.py`. No human message between dispatch and the coordinator's final report.

## 3. Design choices and why

1. **Checklist before code.** The shipped checks are a partial sample. A separate seat that
   turns the spec into numbered, cited requirements and flags the ones no shipped check
   covers gives the reviewer a target that is the spec, not the tests.
2. **Reviewer builds from RUN.md in a clean checkout.** Gate 3 is "builds and serves from a
   clean container by following RUN.md", so the reviewer rehearses exactly that on every
   revision.
3. **Lessons travel inside handoffs.** Seats only see messages addressed to them, so a
   lesson that is not pasted into the next handoff does not exist for the implementer.
   `retro` sends standing rules to the coordinator before each unit.
4. **Coordinator never codes.** Keeps work distributed and keeps the acceptance decision
   separate from authorship.
5. **Stage freeze is explicit.** The coordinator announces a frozen revision before the next
   spec enters the room, so the room log shows ordering.
6. **Quiet turns and model failover (`factory/acp-quiet.py`).** Band's OpenCode runtime
   posts the text a seat ends its turn with as a reply, which wakes the sender; free models
   rarely end on empty text, so bare "no action needed" replies used to bounce between
   seats (191 of 221 messages in a practice run). Each seat's OpenCode process runs behind
   a small pass-through ACP proxy that drops the end-of-turn text only when all of it is a
   bare acknowledgement (short, no verdict, revision or code), and that switches the seat
   to its next listed model when the free tier reports a usage limit or upstream failure.
   It never writes or edits content: every message, tool call and commit is the agent's.
   Each decision is logged per seat.
7. **Generic mandates.** No product, endpoint, field or error vocabulary in any mandate;
   all track detail arrives in the dispatch. `harness check` mandate scan passes on these
   files.

## 4. Setup (another team can follow this)

1. Install Band Desktop, sign in, enable one coding-agent harness the operator has model
   access for.
2. Create four local agents named exactly `coordinator`, `implementer`, `reviewer`, `retro`.
   Paste each mandate as that agent's instructions and set `Harness:`, `Model:`, `Effort:`
   in each mandate file to the real values.
3. Run `factory/create_seats.sh <run folder>` (creates the seats, links the mandates,
   sets models and launches them through `factory/acp-quiet.py`). The run folder holds
   only the result repository.
4. Give each seat its own Git identity; give all seats the absolute path of the result
   repository and permission to run Git, Docker and the harness.
5. Create one fresh room, add the four seats, then paste the stage-1 dispatch.
6. Follow `factory/RUNBOOK.md` for checks, export and the live artifact.

## 5. What we tried that failed

Measured in the practice runs and the submitted run:

- **Acknowledgement loops.** Band's OpenCode runtime posts a seat's end-of-turn text as a
  reply, which wakes the sender. Free models rarely end a turn on empty text: in one
  practice run 191 of 221 room messages were bare acknowledgements. Mandate rules alone did
  not stop it; the seat proxy (§3.6) does, but some shapes still slipped through (§9).
- **Some free models cannot end a turn without a tool call.** big-pickle and nemotron loop
  on `true`: the stage-2 implementer made 135 such calls in one turn (169 in the stage),
  the stage-1 retro 71. big-pickle was removed from the implementer's fallbacks after stage 2.
- **One turn per handoff part.** Handoffs exceed the room's ~5,000-character message cap, so
  they are sent as verbatim numbered parts. Each part used to cost a full model turn on the
  receiving seat (26 turns for one stage-3 handoff), which used up free quotas and gave
  weak models 25 chances to post junk. Since stage 3 the proxy assembles the parts into one
  prompt.
- **Free-tier limits.** Limits are per model and recover over time; large prompts are
  refused first. In stage 3 the implementer's three models and later the reviewer's three
  models were all limited at once; in stage 4 a 104K-character handoff was refused by three
  models and accepted by a fourth.
- **Interrupting a seat can lose its message.** `band runtime interrupt` settles the message
  of the cancelled turn as processed (stage 4, §8).

## 7. How the factory detects, rejects and recovers from bad work


- Detect: reviewer's clean build, supplied checks, and probes for every UNTESTED checklist
  item; reviewer also looks for code keyed to test inputs.
- Reject: a REJECT verdict carries requirement text, observed vs expected behaviour and a
  reproduction, and is copied to `retro`.
- Recover: implementer reproduces, fixes the cause, adds a probe, commits anew (no amend);
  `retro` records the root cause and a generic rule; repeated causes become standing rules
  that ride in every later handoff.
- Real example (stage 2): the implementer reported `be11ee3` with the supplied checks green
  (stage 1 122/122, stage 2 12/12). The reviewer's own probe of checklist item 25 found that
  candidates were deduplicated by value alone instead of one per supporting page, and sent
  REJECT at 13:06:59 UTC with the code location (`selection.py`). The coordinator routed it
  to the implementer and retro (13:07:23); retro recorded the lesson (`57b9abf`, 13:07:35);
  the implementer fixed the dedupe key (`2cd5de3`, 13:21:04); the reviewer re-ran and
  accepted (13:25:57). The supplied checks never caught this; the reviewer's probe did.
- The same lesson was pasted into the stage-3 and stage-4 handoffs by the coordinator, and
  the stage-3 reviewer re-verified it.
- Stage 4: the implementer's own harness run on `b51897c` was green on every stage. The
  reviewer's ten independent probes found five failing requirements (S4-21/22, S4-29/30
  `corroborated_since`, S4-51 investors on the history screen) and sent REJECT at 17:44:44 UTC.
  The fix `f000d83` introduced a regression in S4-28 (member `corroborated` computed from
  standing origins instead of current candidates); the reviewer rejected it at 18:02:19, the
  implementer had already corrected it in `cd6208c`, and the reviewer accepted `cd6208c` at
  18:07:06 after re-running the harness and all ten probes. retro recorded both root causes
  (`c1e7b51`, `5c67a43`).
